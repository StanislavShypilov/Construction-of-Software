# ADR-002: Ізоляція сезонного ціноутворення та туристичного збору

- **Статус:** прийнято
- **Завдання:** 4 — Polymorphism + Protected Variations

## Контекст

Початковий `LegacyHotelManager` використовував ланцюжок `if/else` для визначення сезонного множника (`Peak`, `High`, `Low`). Зміна сезонного правила вимагала редагувати центральний процедурний метод. Розрахунок туристичного збору також був зашитий безпосередньо в процедурний код.

## Рішення

1. Додати `SeasonPricingPolicy` із реалізаціями `LowSeasonPricingPolicy`, `HighSeasonPricingPolicy` і `PeakSeasonPricingPolicy`.
2. `Room` делегує розрахунок об'єкту політики замість вибору множника через каскад умов.
3. `SeasonPricingPolicies` обирає реалізацію за назвою сезону через реєстр фабрики.
4. Додати `TouristTaxPolicy` та `StandardTouristTaxPolicy`; `Booking` використовує контракт, а не фіксує ставку 1% у власному коді.
5. Зберегти `BookingRepository` і `SmsNotifier` як стабільні контракти для деталей зберігання та сповіщення.

## Обґрунтування

Polymorphism означає, що розрахунок виконує відповідна реалізація `SeasonPricingPolicy`. Protected Variations ізолює ймовірні зміни сезонних множників, правил збору, способу збереження та SMS-провайдера за контрактами. Додавання нового сезонного алгоритму не вимагає змінювати метод розрахунку в `Room`.

## Наслідки

- **Позитивні:** алгоритми розрахунку ізольовані; залежності явні; правила можна перевіряти окремо.
- **Компроміси:** додано кілька невеликих класів та фабрику; вибір сезонної політики все одно має відхиляти невідомі значення.
- **Обмеження поточної демонстрації:** номер кімнати та базова ціна досі задані в application-сценарії; справжній каталог доступних номерів не реалізований.
